# Phase 0 阶段记录：数据工程

记录日期：2026-11-04（UTC）。本阶段产出 `data_loader.py`、`data/manifest.json` 与 `data/processed/*.parquet`，供后续所有阶段读取。复现命令见文末。

## 1. 数据源选择与回退链

本会话环境中，Binance REST 接口（`api.binance.com`、`fapi.binance.com`）返回 HTTP 451（地区限制），Bybit 被出口代理拒绝（403），OKX REST 与 Binance 官方公开数据归档 `data.binance.vision` 可达。因此主数据取自 `data.binance.vision` 的月度 zip 归档。该归档与 REST `/klines` 是同一份交易所数据，并且每个 zip 附带官方 `.CHECKSUM`，可做逐文件 SHA256 校验，可审计性优于 REST 分页拉取。`data_loader.py` 中实现了完整回退链：本地 Parquet 缓存 → Binance Vision 归档 → Binance REST → OKX REST，任何一级失败自动降级并在 manifest 中记录来源。

交易品种选用 Binance USDⓈ-M 永续合约 `BTCUSDT` 与 `ETHUSDT`。理由是任务给定的费率结构（taker 5bp、maker 2bp）与 Binance 期货 VIP0 一致，且 ≤1.5x 杠杆在现货上需要借贷，在永续上是原生能力。永续合约多头持仓需要支付资金费率，因此同时下载了官方资金费率归档，后续回测会把资金费用计入持仓成本，避免只做多策略在牛市高资金费率期间被系统性高估。现货 1H 数据仅用于两件事：2019 年慢速价格类指标预热，以及永续-现货基差交叉校验；现货不参与任何成交量分布计算和交易。

## 2. 下载与完整性校验

共下载并校验 680 个官方 zip 文件，全部 SHA256 与官方 `.CHECKSUM` 一致。

| 数据集 | 区间 | 行数 | 源文件数 |
|---|---|---|---|
| BTCUSDT 永续 1H | 2020-01-01 00:00 → 2026-10-31 23:00 | 59,903 | 82 |
| ETHUSDT 永续 1H | 2020-01-01 00:00 → 2026-10-31 23:00 | 59,903 | 82 |
| BTCUSDT / ETHUSDT 官方 4H（仅交叉校验） | 同上 | 14,970 / 14,970 | 82 / 82 |
| BTCUSDT / ETHUSDT 资金费率 | 2020-01-01 00:00 → 2026-10-31 16:00 | 7,488 / 7,488 | 82 / 82 |
| BTCUSDT / ETHUSDT 现货 1H（预热与校验） | 2019-01-01 00:00 → 2026-10-31 23:00 | 68,605 / 68,605 | 94 / 94 |

研究区间 `[2020-01-01, 2026-11-01)` 应有 59,904 根 1H K 线。最后一根 1H 的开盘时间为 2026-10-31 23:00，收盘于 2026-11-01 00:00，正好覆盖任务要求的终点。

解析层处理了归档格式的三处不一致：期货 CSV 自 2022 年起带表头而早期不带；现货 CSV 自 2025-01 起时间戳由毫秒改为微秒；资金费率 `calc_time` 存在毫秒级抖动（例如 `...800002`），统一四舍五入到整分钟。

## 3. 发现的问题与处理

第一个问题是归档缺口。2026-10 永续月度归档缺失 2026-10-28 全天 24 根 1H（BTC 与 ETH 同时缺失）。进一步核查日度目录后确认，Binance Vision 当天的期货 K 线、1m、逐笔成交、标记价格日度文件全部未发布，而现货日度文件完整，说明这是归档发布缺口，不是交易所停机。该缺口落在 OOS 区间内，若保留空洞，持仓在这 24 小时内将无法被止损撮合，回测会失真。处理方式是按回退链用 OKX USDT 永续（`BTC-USDT-SWAP` / `ETH-USDT-SWAP`）1H 补齐，成交量按缺口开始前 168 根 1H 上“Binance 成交量 / OKX 成交量”的中位数缩放（BTC 1.836，ETH 1.271），缩放系数只使用缺口之前的数据。补齐行逐行标记 `fill_source = okx_swap`。补数质量用独立来源 Binance 现货检验：补齐的 24 根收盘价相对现货的中位差为 BTC -3.96bp、ETH -4.27bp，最大绝对差 6.2bp / 5.8bp，与全样本永续-现货常态基差（中位 -3.8bp / -3.7bp）一致。规则上，只有 ≥6 小时的连续缺口才视为归档缺口进行补齐，更短的缺口视为真实停机，保持缺失、不伪造 K 线。

第二个问题是维护期占位 K 线。2024-10-28 20:00 的 1H K 线成交量为 0 且 O=H=L=C（BTC 与 ETH 均如此），是交易所维护期间的占位数据。Binance 官方 4H 聚合同样排除了这根 K 线（该 4H 的开盘价取自 21:00 的 1H），因此清洗时将其剔除，这也是清洗后唯一保留的缺失小时。

第三个问题是官方 4H 归档自身的错误。策略使用的 4H 由 1H 在本地按 UTC 00/04/08/12/16/20 对齐聚合（`label=left, closed=left`），保证两个周期同源；官方 4H 仅用于交叉校验。14,970 根共同 4H 中，开高低价全部逐位一致，仅 BTC 2023-11-10 12:00 一根的收盘价与成交量不一致（官方 4H 收盘 37118.4、成交量 68,307；1H 聚合收盘 37092.6、成交量 80,360）。下载当日官方 1m 归档重新聚合 240 根 1m K 线，结果与 1H 聚合逐位一致，裁决为官方 4H 归档有误，本地聚合正确。其余仅有 2022-07-16 04:00 一根的成交量差异（BTC 0.05%，ETH 0.014%），对成交量分布无实质影响。

现货数据存在 59 个缺失小时（20 段，均为 2019–2023 年真实维护停机）和 9 根维护期不完整小时 K 线。现货不参与交易与成交量分布计算，这些问题不影响策略，仅记录在案。

## 5. 对后续阶段生效的约定

时间戳统一为“索引 = UTC 开盘时间”，并显式提供 `close_time = open_time + interval` 列。4H 数据对 1H 策略可见的条件是 `close_time ≤ t`，这条约定将在 Phase 1 的跨周期对齐中强制执行，并由防未来函数测试验证。成交量分布只使用永续成交量，不跨市场拼接，因此 2020 年 1 月初第一组枢轴确认之前不会出现箱体，这是诚实的指标预热期。

## 6. 复现方式

```bash
pip install -r requirements.txt
```

```bash
python data_loader.py --build
```

```bash
python data_loader.py --verify
```

`--build` 会重新下载全部官方归档并逐文件校验 SHA256，然后重建 Parquet 与 `data/manifest.json`；`--verify` 核对仓库内 Parquet 文件与 manifest 中记录的 SHA256 是否一致。原始 zip 不入库（`.gitignore` 排除 `data/raw/`），处理后的 Parquet（约 19MB）入库，便于在无网络环境下直接复现后续全部结果。
